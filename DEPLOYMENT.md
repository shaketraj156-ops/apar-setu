# Deploying SNAP — Render (backend) + Vercel (frontend)

Deploy the **backend first** (you need its URL for the frontend), then the frontend, then
come back and tell the backend the frontend URL (CORS).

## 0. Before you start
- A Supabase project with `database/migrations/001_schema.sql`, `002_rls.sql`,
  `database/views/003_reports_views.sql` and `database/seed/seed_data.sql` applied.
- Code pushed to GitHub (`render.yaml` is at the repo root, `frontend/vercel.json` in the frontend).
- Generate secrets locally (prints only, writes nothing):
  ```
  cd backend && venv\Scripts\python scripts\generate_prod_keys.py
  ```

## 1. Backend on Render
1. Render dashboard → **New → Blueprint** → pick this repo. It reads `render.yaml`.
2. Fill in the secrets Render asks for (all marked `sync: false`):

| Variable | Value |
|---|---|
| `DATABASE_URL` | Supabase → Project Settings → Database → connection string (pooler, URL-encode the password) |
| `SUPABASE_URL` | `https://<ref>.supabase.co` |
| `SUPABASE_ANON_KEY` / `SUPABASE_PUBLISHABLE_KEY` | Supabase → API keys |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase → API keys (**server only**, never in the frontend) |
| `SUPABASE_JWT_SECRET` | Supabase → API → JWT secret (fallback for token checks) |
| `QR_PRIVATE_KEY_PEM`, `QR_PUBLIC_KEY_PEM` | from `generate_prod_keys.py` |
| `CORS_ORIGINS` | your Vercel URL, e.g. `https://snap.vercel.app` (no trailing slash; comma-separate several) |
| `QR_BASE_URL` | `https://snap.vercel.app/verify?t=` |

`JWT_SECRET` and `SIGNING_SECRET` are generated by Render. With `ENV=production` the API **refuses to start**
if a secret is weak, the DB is SQLite, the QR keys are missing, or CORS still points at localhost — check the
deploy log if it fails on boot.
3. After deploy, open `https://<service>.onrender.com/health` — it should return `{"status":"ok", ...}`.
   Note: the free plan sleeps after inactivity, so the first request can take ~30–60 s.

## 2. Frontend on Vercel
1. Vercel → **Add New → Project** → import the repo, set **Root Directory = `frontend`**
   (framework Vite is auto-detected; `vercel.json` handles SPA routing so refreshing `/login` works).
2. Environment variables:

| Variable | Value |
|---|---|
| `VITE_API_BASE_URL` | `https://<service>.onrender.com` (no trailing slash) |
| `VITE_SUPABASE_URL` | same Supabase URL |
| `VITE_SUPABASE_ANON_KEY` | the **anon** key only |
| `VITE_ENABLE_DEMO` | `true` only if you want public demo logins |
| `VITE_DEMO_PASSWORD` | a throwaway password used only by the demo accounts (it is public in the bundle) |

3. Deploy, then copy the Vercel URL into Render's `CORS_ORIGINS` / `QR_BASE_URL` and redeploy the backend.

## 3. Supabase settings
- Authentication → URL Configuration: set **Site URL** to the Vercel URL and add it to Redirect URLs.
- If you enable the demo, run `DEMO_PASSWORD=<same as VITE_DEMO_PASSWORD> python database/seed/create_demo_users.py`
  against the production project (needs `backend/.env` with the service-role key; run locally).

## 4. Smoke test (after both are live)
1. Open the site → Login → each demo role lands on its dashboard and data loads.
2. Student sees only their own record; AICTE sees reports + audit logs; verifier can verify a QR.
3. `curl https://<service>.onrender.com/api/v1/audit/logs` must return **401**.

## Known limitations
- `GET /credentials/qr/{record_id}/png` is intentionally unauthenticated (the Student page uses a plain
  download link). It only returns a signed QR with a masked APAAR ID and needs the record UUID.
- Free Render instances sleep; use a paid plan for the real launch.
